# Implementation plan: OCE-managed native OpenClaw plugins

- **ID:** RFC-0023
- **Delivery status:** Planned
- **Owner:** OCE Plugin, Credential, Sandbox, Compute, Console, and runtime maintainers
- **Authority:** [OCE-managed native OpenClaw plugins](../rfcs/0023-managed-native-openclaw-plugins.md)
- **Source baseline:** `000aa1d6b80103d7cccac9598ea628deee389098`

## Outcome and scope

An administrator can select a reviewed Google integration, connect an authorized Google identity, choose services and action access, and deploy an OpenClaw Agent. The Agent's dedicated Harness worker can use [gog](https://github.com/openclaw/gogcli), OpenClaw's command-line client for Google Workspace APIs, or write its own scripts under the same enforced policy. Implementation can proceed in increments, but P0 release requires the complete action and scope surface of the selected `gog` release, including required credential modes. The administrator selects the services and permission level for each Agent; full product coverage does not grant every Agent every scope.

The [PluginDriver contract](../../docs/reference/drivers/plugin.md) owns catalog and policy validation; OpenClaw Control Plane (OCC) owns Agent selections and revisions, and Compute owns runtime preparation. The [credential source](../../docs/reference/credential-sources.md), [OpenShell Credential Gateway](../../docs/reference/drivers/openshell-credential-gateway.md), and [OpenShell Sandbox](../../docs/reference/drivers/openshell-sandbox.md) are the credential and enforcement touchpoints. Extend their existing lifecycle through supported callers. Prompt-time approval and granular per-tool permission parity are outside P0.

## Delivery steps

Each numbered step is a logical PR scope. Steps 1–9 form P0. Steps 10–11 cover ClawHub discovery and delivery; step 12 is a separate later MCP phase.

1. **Catalog and Agent binding.** Extend the selected OpenClaw Plugin Driver to describe the reviewed Google integration, its skill, compatible runtime artifact, and connection requirements. Extend Agent selection and deployment admission to bind the exact catalog release, mapping version, connection reference, chosen services, and action access to an immutable Agent revision. Require authority for the Agent and selected connection; keep credential values out of selections and revisions.
2. **OAuth connection lifecycle.** Let an operator manage multiple reusable OAuth client configurations in a Namespace, each backed by a Secret for the client ID and client secret. Add the browser authorization flow through the existing credential lifecycle. The Credential Refresh implementation performs the code exchange and places refresh material directly with the selected provider, which owns the only durable copy and subsequent refresh. Record observed granted scopes separately from requested scopes. Align with the [personal Agent OAuth proposal](https://github.com/openclaw/openclaw-enterprise/pull/3068) while preserving the selected Agent's access model. Resolve uncertain exchange outcomes without replaying rotating refresh tokens.
3. **Console selection.** Extend the Agent Plugins workflow to select a saved connection or create one using a Google OAuth application. For a new user-consent connection, present the scope inventory from step 6 by product, with initial selections based on the chosen products and read-only or all supported actions. Allow product-wide and individual selection, plus custom scope entry; send the final scope set in the Google authorization request. Before deployment, show missing grant scopes, unavailable actions, provider prerequisites, and the reviewed destinations and operations associated with custom scopes. Enforce the selected Agent action policy even if a saved grant or custom scope is broader.
4. **Worker environment.** Upstream the normal worker launch behavior needed to propagate approved placeholder variables, proxy settings, and the trust bundle to tool processes while excluding model credentials. Expose nonsecret variable names, granted scopes, and selected action metadata to the Agent, not the placeholder value in the model conversation.
5. **Runtime packaging and skill.** Pin and verify `gog` in the dedicated Harness worker image; deliver the reviewed skill to its Agent workspace only when selected. Run `gog` and generated scripts on the worker, without installing a Google extension on the Agent Gateway. The skill points to the baseline command, supported capability metadata, and an Agent-owned durable location for generated scripts. Index script purpose, arguments, required scopes, and last validation so a fresh conversation can reuse it. Cache public provider schema by API version when used, without a credential. Use the applicable [workspace storage](../../docs/reference/drivers/kubernetes-compute/storage-and-credentials.md) for the execution topology; a replacement pod must preserve same-Agent reuse and cross-Agent isolation.
6. **Google operation inventory.** Google integration maintainers generate candidates from the selected `gog` release and provider metadata, then review the mapping from service, action, required scopes and identity prerequisites to destination and API operation. Publish a product-grouped OAuth scope inventory covering the pinned release. A CLI release pin does not bound the provider methods reachable through `gog api call`; define and version the supported provider-operation universe separately. Every supported operation and authentication mode must be accounted for before release. Unknown operations fail closed, and HTTP method alone does not classify an action as read or write.
7. **Credential modes and destinations.** Add the credential capabilities required by that inventory, including provider-specific account, entitlement, administrator consent, or service-account prerequisites. Support the reviewed destinations under one connection without creating multiple refresh owners. Resolve the required credential mode and grant for each selected operation; admit its reviewed API destinations with the Agent binding, including when it uses a custom scope. Refuse unrepresentable selections.
8. **Compile and enforce action policy.** Compile the reviewed mapping and Agent selection into request-level OpenShell egress controls. Authorize the effective request before credential injection, including all policy contributions and credential aliases for the same identity. Both `gog` and admitted script interpreters must reach the same enforcement boundary. Refuse broader overlapping policy contributions that widen the selected action set, uninspectable multiplexed requests, and policy forms the deployed OpenShell version cannot enforce; denied operations must not receive the credential or reach the provider through an alternate admitted path.
9. **Ordinary deployment and qualification.** Compose the selected skill, runtime artifact, connection, policy, and workspace through Agent deployment, readiness, replacement, and retirement. Withdraw the binding and policy when the selection is removed, without affecting other Agents using the same connection. Qualify the entire P0 inventory and its credential modes before release. Update the owning Plugin, Credential, Sandbox, Compute, Console, and runtime reference and flow documentation in their implementation PRs.
10. **ClawHub discovery.** Add search and details through the Plugin Driver. Show compatibility and admission status, including unsupported capability classes. Registry discovery grants no installation or execution authority.
11. **ClawHub release lifecycle.** Admit an exact reviewed release and its complete capability and dependency set; bind it to the Agent revision and verify its artifact before Compute materializes it. Release updates require a new review and Agent revision. Preserve restart from an already-admitted artifact when the registry is unavailable.
12. **Credentialed MCP discovery and enforcement.** Use a connection to discover candidate remote Model Context Protocol tools, bind the reviewed tool set and server identity to policy, and enforce allowed `tools/call` names before forwarding and before any credential injection. Tool discovery is not authorization; servers that multiplex different actions behind one name need enforceable argument semantics or remain unavailable.

## Verification

For P0, exercise the ordinary Console-to-Agent deployment on a supported Kubernetes/OpenShell stack with authorized test identities for each distinct credential and enforcement path. Verify that the authorization request matches the final product, individual, and custom scope selections. Exercise allowed provider operations through both `gog` and a model-written script, including one that requires a granted custom scope, representative cross-service reads, and an authorized reversible write. Using the same connection as the custom-scope operation, assert that an unadmitted destination and a disallowed operation are rejected before credential injection, even with a broader saved OAuth grant. Cover read operations that use POST, alternate credential aliases, multiple destinations, grant mismatch, unauthorized connection selection, refresh failure, and a second Agent without the selection. Replace the worker and start a fresh conversation to verify the same Agent can discover and reuse its script without exposing secrets or model credentials.

Release qualification must reconcile the complete reviewed operation inventory against supported scopes, identity modes, permission choices, and enforceable policy. A representative live workflow establishes deployment and request behavior; inventory checks establish coverage of the declared surface. Report these as separate evidence and identify any untested provider prerequisites. Later ClawHub and MCP work needs its own installed-artifact and allowed/denied request proof.
