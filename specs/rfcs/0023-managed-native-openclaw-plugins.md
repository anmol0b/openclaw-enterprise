# RFC-0023: Managed native OpenClaw plugins

- **Created:** 2026-10-21
- **Implementation plan:** [Managed native OpenClaw plugins](../plans/0023-managed-native-openclaw-plugins.md)

## Summary

OpenClaw Enterprise (OCE) should let an administrator select a reviewed Agent integration, bind an authorized connection, and deploy both through the Agent revision lifecycle. The first milestone (P0) pairs a reviewed skill with pinned [gog](https://github.com/openclaw/gogcli), OpenClaw's command-line client for Google Workspace APIs. The model can use gog or write reusable API scripts; OpenShell enforces the same admitted operations and credential boundary. Platform integrations remain OCE-managed.

## Plugins and capabilities

OpenClaw uses _plugin_ broadly. An extension can register tools, channels, model providers, hooks, and other runtime behavior. Code loaded in a Gateway shares its trust boundary. A _skill_ supplies model instructions, a CLI runs through an execution tool, and a Model Context Protocol (MCP) server exposes tools over a protocol. They run in different trust boundaries.

An **OCE integration** is an administrator-selectable Plugin Driver catalog entry that associates reviewed components with connection requirements, placement, and access choices. A separate marketplace service is not required. The [Plugin Driver](../../docs/reference/drivers/plugin.md) supplies catalog and policy validation; OpenClaw Control Plane (OCC) owns Agent selection and revision admission; Compute owns runtime preparation and activation. The current [native plugin path](../../docs/flows/agent-plugins.md) prepares the curated Diffs extension for embedded OpenClaw. It snapshots selection and policy while resolving release metadata at startup. Google needs a dedicated worker behind OpenShell, an admitted artifact identity, a connection binding, and enforced request policy.

Agent-selectable third-party releases may provide reviewed skills, tools, and executable dependencies when their runtime code executes in an admitted worker or sandbox. Review the complete release and dependencies: skill instructions can steer authority the Agent already has. Gateway-loaded code requires separate platform-managed review and admission. Channels, webhooks and routing; model and memory providers; interception; background services and scheduling; Gateway administration; and Harness, Sandbox, or security-policy extensions remain platform-managed. A Slack channel or a Codex Harness integration can technically use an OpenClaw plugin while retaining OCE ownership of its platform authority.

For Google, an OCE runtime release supplies pinned gog in the worker image. Selecting the integration activates the reviewed skill, connection binding, and effective access profile. The worker receives the admitted non-model placeholder and required certificate authority (CA) trust; model and platform credentials stay isolated. If any required component or enforcement capability is absent, activation fails. The skill directs the model to a durable Agent workspace index before generating scripts. Generated workflows and the [gog API caller's 24-hour disk cache](https://github.com/openclaw/gogcli/blob/ec34fedc23dd9d3e90f0401144cec42e06a50783/docs/commands/gog-api-call.md) can persist across redeployment under Agent workspace rules. Disabling the integration withdraws its skill, binding, and policy contribution while retaining workspace data under those rules.

**ClawHub** is an external OpenClaw ecosystem registry and a later discovery source. OCE can expose public search and details with compatibility and admission status. OCE must verify an exact release, classify the complete artifact and dependencies, admit the placement and capabilities, and deliver it through managed deployment. Publisher updates require new release admission and Agent deployment. A registry outage must not prevent deployment of an admitted release. Qualify anonymous access in the target environment; private registry access is outside P0.

## Credentials and connection ownership

An operator can register multiple OAuth applications in one OCE Namespace, with each client ID and secret stored as a Kubernetes-backed OCE Secret. An administrator chooses the application, Google services, and access level when creating a connection, or selects an existing connection whose use is authorized. OCE requests the scopes associated with that choice and shows the effective access, accounting for [scopes actually granted by Google](https://developers.google.com/identity/protocols/oauth2/web-server#step_6_check_which_scopes_users_granted) and other prerequisites.

At consent completion, the paired Credential Refresh implementation exchanges the authorization code and deposits the refresh grant and required client authentication material directly into the selected credential provider. That provider is the refresh grant's first durable home and sole refresh custodian; OpenShell fills this role for Google. OCC stores the source reference and connection metadata, including observed granted scopes, and marks the connection ready only after custody succeeds. This extends the separation in the [Credential Refresh design](0016-sandbox-credential-injection/credential-refresh.md). The [personal Agent OAuth proposal](https://github.com/openclaw/openclaw-enterprise/pull/3068) addresses a related consent and custody flow; align the shared mechanics while keeping its personal-Agent policy distinct.

OCC authorizes the source binding, records the selected connection and access profile in the Agent revision, and attaches the ready source during deployment. The skill identifies the credential variable name, such as `GOG_ACCESS_TOKEN`, and the effective access profile. The worker receives a placeholder; OpenShell supplies a short-lived bearer token only to an allowed request at the bound destination. Tokens, refresh grants, and client secrets stay out of model context, saved scripts, logs, and Agent configuration. The model needs the variable name, not the placeholder value. Authorized Agents may share a connection; withdrawing one binding must not alter another Agent's access. A connection makes its authority available to work executed within that Agent's effective sandbox boundary.

## Plugin limits and enforcement

The administrator selects Google services and either read-only or all supported actions for those services. OCE's Google integration owner maintains a reviewed, versioned mapping from supported actions to required scopes, credential modes, prerequisites, and enforceable operations. The platform core owns generic validation, admission, policy compilation, and deployment. Catalog metadata and API schemas provide candidates for review; they do not confer authority.

P0 covers the full Google API action and scope surface supported by the pinned gog release. This includes services that require [Workspace service-account credentials](https://github.com/openclaw/gogcli/blob/ec34fedc23dd9d3e90f0401144cec42e06a50783/docs/commands/gog-auth-add.md), as well as user-consent flows. Full product coverage does not request every scope or grant every Agent every action. For each Agent, OCC admits the selected actions that the actual grant and prerequisites support, presents exclusions before deployment, and binds the profile version to the revision and connection. A broader saved grant cannot widen that selection.

For REST APIs, OCE compiles admitted operations into OpenShell policy using the approved origin, normalized path template, HTTP method, and any supported query constraints needed to identify the operation. The method identifies a request; it does not classify it as read or write. For example, a read operation that uses POST remains eligible if the trusted enforcement boundary can distinguish it. OpenShell must deny requests outside the effective policy before forwarding and inject credentials only for authorized requests to their bound destinations. Qualify policy in enforce mode across every path to the authority, including provider-contributed rules and overlapping allows. The same rule covers gog commands, `gog api call`, and model-written scripts. Public API schema retrieval uses no credential.

An operation allowlist bounds API operations, not every higher-level workflow or argument. A shared route that selects actions inside its body, such as [Gmail batch requests](https://developers.google.com/workspace/gmail/api/guides/batch), requires a trusted boundary that checks every inner operation; admitting its outer URL alone would expand authority. An action without an enforceable path is a P0 coverage gap to resolve, not an implicit wildcard. Refuse incompatible shared-source configurations without changing other Agents' access. Record the Agent, revision, connection, and decision without credentials or private response data.

This design accepts maintenance of a Google-specific operation mapping. Provider scopes alone can exceed an Agent's selection, and instructions or CLI flags cannot constrain a model-written script. A mandatory action wrapper could mediate each request, but it would also require blocking direct scripts and maintaining provider-specific invocation code.

Remote MCP is later work. Discovery with a credential intended for an approved server can expose candidate tool names through [`tools/list`](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#listing-tools); an administrator selects and admits them. The deployed boundary must enforce the allowed name for `tools/call` and any alternate path to the same authority. [Upstream OpenShell](https://github.com/NVIDIA/OpenShell/blob/20cb306d3ae864f82a91784c8cccb8d33b75b5f4/docs/how-it-works/policies/network-rules.mdx#L499-L542) documents tool-name matching over Streamable HTTP without argument filtering; qualify that support in the deployed runtime. A trusted server or dispatcher must enforce restrictions on actions selected by tool arguments. Discovery metadata does not establish trusted read/write classifications.

Other providers and multiple end-user Google accounts on one Agent are later work. Per-action approval, reviewer routing, OpenClaw elicitation, and general granular tool-permission parity are outside P0. A restriction denies the action; it does not ask for approval. Existing [plugin approval policies](0014-plugin-policy-enforcement.md) remain a separate contract.

## Delivery and open decisions

A local PoC used a temporary worker patch and custom image to exercise live Gmail reads with OpenShell credential refresh and placeholder injection. A deployed Agent used gog and reused model-written scripts across conversations and redeployment. The [implementation plan](../plans/0023-managed-native-openclaw-plugins.md) assigns the ordinary deployment path, full Google coverage, and enforcement qualification to separate workstreams, followed by ClawHub and remote MCP.

The Google integration owner must define the provider-operation universe that measures full coverage. Pinning gog fixes its CLI commands, but `gog api call` discovers provider operations dynamically. Reviewers must version the provider metadata and operation set independently, account for every supported action and credential mode, and define how changes enter admission. No newly discovered operation becomes authorized automatically.

The Sandbox and credential owners must establish that their deployed OpenShell version can represent and enforce every admitted selector after all policy contributions are composed. The credential owners must resolve multi-host binding, code-exchange failure recovery, and required credential modes while retaining sole refresh custody and cross-Agent isolation. These decisions determine whether P0 can meet its full-coverage release gate.
